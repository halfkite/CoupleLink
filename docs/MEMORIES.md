# 相恋日期、纪念日与聊天搜索（1.0-r9 本地修正版）

## 已确认方案与调研

用户于 2026-10-28 确认全部四项功能，并选择纪念日包含定时提醒。保留 Vue 3 / TypeScript / Capacitor、Go 与 PostgreSQL，无新增运行依赖或外部搜索服务。

架构：手机界面 → 现有鉴权 API → PostgreSQL。纪念日后台任务每30秒扫描持久化到期时间，生成有唯一键的提醒；前台/原生后台服务读取后发布同一个“消息提醒”渠道，再按设备确认。搜索使用关系范围内参数化 ILIKE 与序号分页，结果上下文不参与聊天同步游标和送达回执。

MVP/实现顺序：相恋日期共享修改 → 纪念日增删改、每年重复、倒计时与定时提醒 → 聊天视口和回到最新箭头 → 全历史搜索和上下文 → 双账号、时区、闰年、冲突、提醒重试与解绑回归。

## 使用

- 首页“设置相恋时间”，或“时光 → 恋爱开始日期”修改；双方共享，使用版本校验，冲突后刷新并重新决定修改。
- “时光 → 纪念日 → 新增”：名称、日期、不重复/每年、可选提醒时间。编辑中可以删除。默认关系时区沿用绑定设置（当前手机绑定使用 Asia/Shanghai）。
- 原始2月29日不会被改写；非闰年按2月28日纪念，下一闰年恢复2月29日。
- 单次日期已过时不再创建未来提醒；每年重复计算下一次。未启用提醒则 next_reminder 为空。
- 消息页“查找聊天记录”检索服务器全部历史，包含中文子串；% _ 和反斜杠按普通字符搜索。每页50条；点结果查看前后各20条，点“回到最新”返回实时消息。
- 读旧消息时新消息不会强制滚动；离底部超过48px显示箭头。历史上下文不会抬高同步游标或误报送达。

## 提醒的实际边界

- 手机联网、系统允许通知及接收服务运行时才可投递；不绕过系统静音、勿扰、渠道设置或强制停止，不承诺精确秒级或常驻。
- 服务端保留24小时内未确认提醒，断连重连后可补收；更旧的提醒不再集中补发。
- 服务端生成去重，按设备确认。发布通知与网络确认并非跨系统事务；若进程恰好在二者间退出，可能再次提示。通知使用固定纪念日通知 ID，更新该条卡片。
- 修改/删除纪念日会使旧版本提醒失效；解绑和会话撤销后不能继续拉取。
- 浏览器预览不会假装发出 Android 通知，也不会确认消费提醒。
- 所有消息、互动、纪念日及静默后台状态共用一个“消息提醒”类别；背景状态自身静默。旧类别迁移保留已有的屏蔽、静音和振动选择，不强行重置系统偏好。

## 部署

必须同时更新 APK 与服务端，新客户端连接旧服务端会明确提示升级。服务启动时以事务升级数据库到 schema 4；已含账号/聊天数据保留。先备份原数据库，再用 server-bundle/deploy 的同一 Compose 项目和原私有环境配置执行 build/up，切勿删除数据库卷。迁移后不要把旧版服务直接接到 schema 4。

本次仍为1.0-r9内部修正；原交付目录不覆盖，新包放在 artifacts/1.0-r9-fix。RPK本次没有新增通信能力。

## 修复说明

【BUG表象】：通知类别多、系统允许声音但应用不响；阅读旧消息时新消息会拉到底部。

【真实根因】：应用以动作类型拆分多个渠道且额外默认禁用声音；旧消息长度监听不检查用户所在位置，直接滚动到底部。振动硬件问题仍未验收，不能据此断言解决。

【修复方案】：只创建一个共享渠道并清理旧类别；移除重复接收开关；系统决定声振。聊天滚动前记录是否在底部，历史窗口与增量缓存分离。日期输入加载时禁用，关系监听采用稳定标识，避免周期性快照覆盖编辑内容。

【修改代码】：交付目录 source-changes.diff 包含相对项目基线的完整 diff；主要文件为 DeviceRuntime.java、InteractionAlert.java、App.vue、ChatPanel.vue、CalendarPanel.vue、core.ts、memories.ts、server/internal/api/memories.go 与迁移004。

【回归校验】：23项 TypeScript 测试；Go vet/真实隔离 PostgreSQL 集成测试；5项原生策略 JVM 测试；本地浏览器双账号流程验证日期共享、带提醒纪念日、113条消息滚动保持、搜索定位及回到最新；签名 APK 构建。上述测试不能代表真实手机声振和系统顶部横幅验收。本次未操作手机。
